The previous 5s sample at14:23:17 of the same PID shows the worker normally waits on mach_msg for asynchronous USB events and also calls IOConnectCallAsyncMethod to submit transfers. The USB run-loop is not continuously busy with PCM fill; sample proportions are not CPU percentages. MIDI writer mostly waits on its condition or short retry backoff. The user-granted latency activity 0.2.131 did not prevent idle MIDI stalls or long callback gaps; it is not a verified fix.

Code search: current USB worker sets user-interactive QoS once; it is not explicitly lowered at idle. Production regression script prohibits `AudioWorkIntervalCreate` and `os_workgroup_*` imports. An AudioWorkInterval experiment would intentionally change that invariant and requires its own bounded, tested branch, not a silent edit. Increasing the USB queue alone does not solve wakeups beyond32ms and could raise latency. Any new scheduling policy should be checked against driver-helper constraints, system responsiveness, power use and active playback, then A/B tested on hardware. No production code change made from this trace.

Follow-up: `NS6USBRealtime.h` already implements workgroup creation/join/start/finish and its standalone test passes on this Mac (`make usb-realtime-test`). It has never been called by `NS6USB.c`; commit `87057de` introduced both the helper and a package regression test that deliberately rejects those imports in the production driver. Apple’s installed AudioWorkInterval header describes intervals for asynchronous realtime work cycles with a real deadline. The USB worker currently waits in `CFRunLoopRunInMode` for hardware completions; there is no interval spanning that wait. Calling start/finish only after a callback arrives cannot, by itself, remove the 69–71 ms wait *before* the worker starts running. Leaving an interval open across an indefinite hardware wait would misrepresent active work. Therefore the existing helper's unit test establishes API availability, not that adopting it fixes the observed stall. Do not turn it on by simply removing the regression guard.

Next discriminating measurement: in the same active-audio trace, correlate each USB completion's hardware wake, scheduler wait, callback timestamp, and queued microframes. Separate delayed callback delivery from delays inside PCM fill/submission. Only if a bounded, periodic software work cycle with a valid deadline can be identified should the isolated AudioWorkInterval variant be compared against the current driver for wake latency, underruns, MIDI faults, CPU and power. The unhelpful `NSProcessInfo` latency-activity experiment in 0.2.131 is not evidence that AudioWorkInterval would work or fail.

The strongest next experiment is a reversible test that keeps the USB/MIDI worker's legitimate periodic transport work scheduled during silence, then repeats these two traces. Before coding, identify where the actual4ms USB deadline starts and ends; do not keep a work interval artificially open while blocked on `CFRunLoopRunInMode`. Measure whether idle USB wake priority/wait improve and whether the MIDI first-error count and LED behavior change, without penalizing audio or power.

## Diagnostic package 0.2.132

First, test the simpler possibility that the existing user-interactive pthread QoS assignment is lost at the audio-to-idle transition. Compile-time-only switch `NS6_IDLE_QOS_REASSERT=1` queues one reassertion when `ns6_usb_set_paused(true)` follows active audio; the USB worker consumes it on its next OUT completion and logs the returned QoS class. The switch defaults to0. It neither changes USB packets nor retries MIDI, and does not add AudioWorkInterval. MIDI gating caution: `NS6MIDIBridge.c` derives its lease from MIDI messages sent *by* an application to the virtual destination, not from applications opening or reading the virtual source. Mixxx can subscribe to input without emitting output first; if input reads are gated by this lease, no hardware event reaches Mixxx to bootstrap normal traffic. That explains why earlier lease-gated polling broke MIDI and why simply disabling EP0x83 reads when `client_active=false` is not a valid fix. `NS6MIDI.c` currently keeps four async reads pending during the USB session. Reducing idle depth is a separate hypothesis, not established by the scheduling trace.

Rollback caveat: after the user ran the 0.2.130 package installer, `pkgutil --pkg-info io.github.maurojuniorr.numark-ns6` reported 0.2.130 but `/Library/Audio/Plug-Ins/HAL/NumarkNS6M1.driver/Contents/Info.plist` still reported 0.2.132, and the on-disk binary SHA256 differed from the checked 0.2.130 package payload. The package receipt alone therefore does not prove a downgrade. The package preinstall removes old Status apps, not the HAL bundle. A verified rollback must first move the 0.2.132 HAL bundle out of the HAL directory, rerun the 0.2.130 installer, then check the installed bundle version and restart of the helper. MIDI recovery comparison: Ghidra's `AJ::inAsyncCompletionRoutine` in the original Ploytec kext replenishes a successful bulk read and releases a failed one without immediately requeuing it in that routine. Its startup queues16 reads. Our `read_complete` always schedules resubmission on `NotResponding`; that submission returns `PipeStalled`, then `ClearPipeStallBothEnds` aborts the other three pending reads. Apple's IOUSBHost `clearStall()` documentation explicitly says pending I/O is aborted and the data toggle resets. The cascade is explained, but blindly copying the vendor's drop-on-error would eventually leave no MIDI reads and lose first-button responsiveness. Before changing policy, a recovery trigger that does not depend on outbound app traffic is needed; the bridge lease observes writes, not readers.
